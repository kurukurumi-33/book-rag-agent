**并且**：你能把每一步「为什么这么做、出问题怎么办」讲清楚。

## 2. 两条铁律

开发和面试都会围绕这两条，**任何时候都不许违反**：

### 铁律一：AI 服务不直连业务数据库

```
✅ 允许：ai-service/app/ 通过 HTTP 调 Spring Boot 的 /api/xxx 拿数据
❌ 禁止：ai-service/app/ 里出现 pymysql / SQLAlchemy 连 book_agent 库
✅ 例外：ai-service/scripts/ 下的开发脚本可以直连（它们是工具，不是服务）
```

**为什么**：业务逻辑（校验、事务、权限）集中在主服务。如果 AI 服务也直连 DB，以后加权限校验要改两个地方。

### 铁律二：业务数据的主人是 Spring Boot

Python 负责「理解」（抽取、向量化、检索、对话），
Java 负责「业务」（增删改查、状态流转、事务）。

Python 的服务是**无状态**的：文本进，结果出，不存业务数据。

## 4. M1 — 抽取落库

### 4.1 目标

把已经能跑的抽取能力（`app/services/extract.py`），变成**数据库里真实存在的结构化数据**。

做完后：`SELECT COUNT(*) FROM book_post WHERE extract_status='DONE'` 应该等于总条数。

### 4.2 数据流

```
Spring Boot                          Python AI 服务
POST /api/posts/extract-pending
   │
   ├─ 查 extract_status='PENDING' 的帖子
   │
   ├─ HTTP POST /extract/batch ─────►  批量抽取（内部并发）
   │◄────── 返回 results 列表 ─────────┤
   │
   ├─ 逐条写回结构化字段
   ├─ 成功的置 extract_status='DONE'
   ├─ 失败的置 extract_status='FAILED'
   └─ 返回统计 {total, done, failed}
```

### 4.3 接口契约

> 字段细节实现后以 **Swagger 为准**（http://localhost:8000/docs）。
> 这里只记 Swagger 表达不了的**设计要点**。

#### 【新增】`POST /extract/batch` — Python 侧

| 入参 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `texts` | string[] | 是 | 帖子原文列表，最多 200 条 |
| `max_concurrency` | int | 否 | 最大并发数，默认 8 |

出参是 `results` 数组，**顺序与请求严格一致**，每项三个字段：
`raw_text`（原样回显）／ `book_info`（失败时 null）／ `error`（成功时 null）。

**设计要点：单条失败不中断整批。** 批量抽取必然有个别失败，
整批抛错等于前面成功的全白跑。调用方靠 `raw_text` 或下标对齐。

错误码：400（空 / 超 200 条 / 并发数 < 1）、500（整批性异常，如 key 失效）

#### 【新增】`POST /api/posts/extract-pending` — Java 侧

编排端点。**主服务主动驱动**，AI 服务只被动响应。

入参 `limit`（默认 50，上限 200）；出参 `{total, done, failed, failedIds}`。

错误码：400（limit 超 200）、**503（Python 服务连不上——必须捕获，不能让它 500 崩掉）**

#### 【已有】`POST /extract` — Python 侧

单条抽取，已实现。留着调试用，字段见 Swagger。

### 4.4 决策点（你拍板）

| # | 决策 | 推荐值 | 影响 |
|---|---|---|---|
| 1 | 一次批量处理多少条 | `limit=50` | 太大容易超时，太小要调很多次 |
| 2 | Python 侧并发度 | 8 | 太大打 429 限流 |
| 3 | 单条失败怎么处理 | 置 `FAILED`，**不重试** | 重试逻辑留到以后再补 |
| 4 | 失败的帖子怎么再处理 | 下次用 `?status=FAILED` 重跑 | 需要的话再加，现在是 PENDING |

**决策记录**（已定，两个数都配在 `application.yml` 里，不写死在代码里）：

```
1. 一批 = 50 条（ai-service.batch-size）
   理由：单条抽取实测约 1 秒，50 条 ÷ 并发 8 ≈ 7 秒。一批的耗时远低于 HTTP 超时线，
        再往上加批量收益递减 —— 反正调用方要反复调，一批小一点失败重跑的代价也更小。

2. 并发度 = 8（ai-service.max-concurrency）
   理由：DeepSeek 单账号并发上限保守估计 10~20，取 8 留一倍余量防 429 限流。
        实测 50 条只用 7.2 秒，说明 8 已经吃满了这一批的并行度，继续加收益递减。

3. 单条失败：置 FAILED，**不自动重试**
   理由：失败原因没解决时自动重试 = 反复烧 token。留个 FAILED 标记可见可查，重试由人决定。

4. 重试方式：手动把那行的 extract_status 改回 PENDING
   （`?status=FAILED` 参数暂不做，220 条实测零失败，没有实际需要）
```

**实测数据**：220 条分 5 轮跑完（50 + 50 + 50 + 50 + 20），**零失败**，单轮约 7 秒，全程不到 40 秒。

### 4.5 验收标准

- [x] 启动 Python 服务后，`curl -X POST localhost:8000/extract/batch` 能返回正确结构
- [x] 调 `/api/posts/extract-pending` 后，数据库里对应条数 `extract_status` 变成 `DONE`
      （没有 `limit` 参数，一批多少条由 `ai-service.batch-size` 决定）
- [x] 抽查 8 条，`book_name` / `price` / `has_notes` 合理；出版社做了归一化
      （外研社 → 外语教学与研究出版社），原文没提的一律 NULL
- [x] **把 Python 服务停掉**再调 `/api/posts/extract-pending` → 返回 **503**，响应体含
      `"AI 服务不可用"` + `Connection refused` 原文 + 排查提示；**Java 服务不崩**（0.019s 返回，不卡超时）
- [x] 重复调同一个接口 → `picked=0`，已 DONE 的不会被重复抽取（幂等）
- [x] 全部 220 条跑完，统计 `DONE` 数量 = 220

## 5. M2 — 语义检索

这是 RAG 的 **R**。分三步走。

### 5.1 M2-1 建索引

#### 目标

把抽取好的结构化字段拼成一段「检索文本」，做 embedding，存进向量库。

#### 为什么不能直接拿 `raw_text` 做 embedding

`raw_text` 里混着「40」「包邮」「可小刀」这些噪音，会稀释掉「高等数学」这个核心语义。
**先抽出干净字段，检索质量才有保证**——这就是 M1 存在的意义。

#### 决策点

| # | 决策 | 结论 | 说明 |
|---|---|---|---|
| 1 | **embedding 模型** | ✅ **本地 BGE `bge-small-zh-v1.5`** | DeepSeek **没有** embedding API，必须另选。见下方备选对比 |
| 2 | **检索文本怎么拼** | ⬜ **待你拍板** | **这是最关键的设计决策**，见下 |
| 3 | 抽取不全的帖子进不进库 | ✅ 只跳过抽不出**书名**的 | 只有成色+价格、没有书名的记录跟「这是哪本书」完全无关，进库就是纯噪音 |
| 4 | 向量库选型 | ✅ Chroma（嵌入式，零配置） | 也可用 FAISS。Chroma 是进程内库，不用起 Docker |

**决策 1 的备选方案**：

| 方案 | 成本 | 说明 |
|---|---|---|
| **本地 BGE**（已选） | 免费 | `sentence-transformers`，首次下载约 100MB（走 `hf-mirror.com`），之后离线。**面试现场断网也能演示** |
| 通义 / 智谱 embedding API | 有免费额度 | 要再注册一个 key，且演示依赖网络 |

**决策 2 的参考拼法**（**不是标准答案**，你可以改，改完用 `scripts/try_search.py` 对比）：
```
高等数学 第七版 同济大学 有笔记 九成新
```
即：`book_name + edition + author + publisher + condition_desc`。
参考思路：**不要**拼 `price`（价格是过滤条件，不是语义特征）、**不要**拼 `raw_text`（噪音稀释核心语义）。

> ⚠️ 这里有个取舍：拼得越多，语义越丰富，但噪音也越多。
> 建议先按上面拼，然后用 M2-3 的测试集验证，不好再调。

#### 接口契约

#### 【新增】`POST /index/build` — Python 侧

| 入参 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `limit` | int | 500 | 最多拉多少条，上限 500（主服务那边的截断值） |
| `rebuild` | bool | false | true = 先清空向量库再建。**只有换模型或改拼法时才需要** |

出参：`{fetched, indexed, skipped, collection_count, dim, elapsed_ms, note}`

**设计要点**：

1. 按铁律一，帖子数据**调 Spring Boot 的 `GET /api/posts?extractStatus=DONE`** 取，不直连数据库。
2. 写入用 `upsert` 且 **id = 帖子数据库主键**，所以**重复调用是幂等的**，不需要先清库。
3. `metadatas` 里只存「列表页直接能显示」的字段（`book_name` / `publisher` / `price` / `has_notes`…）。
   帖子详情仍然回主服务 `GET /api/posts/{id}` 取 —— **向量库是索引，不是业务数据的副本**，
   这样就绕开了「同一份数据存两处、要保证一致」的麻烦。

#### 验收标准

- [x] 能一次把所有 DONE 的帖子灌进向量库（实测 220/220，6.4 秒，**不花 LLM token**）
- [x] 重复调用不会产生重复向量（第二次跑完仍是 220，不是 440）
- [x] 向量库记录里能对回主服务（`post_id` → `GET /api/posts/{id}` 通）

### 5.2 M2-2 检索实现

#### 接口契约

#### 【新增】`POST /search` — Python 侧

| 入参 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 自然语言查询，**不需要跟帖子用词一致** |
| `top_k` | int | 否 | 返回条数，默认 10，上限 50 |
| `min_score` | float | 否 | 相似度阈值，低于此值不返回。不传则用服务端默认阈值 |

出参 `{query, min_score, count, hits[]}`，`hits` 每项：
`post_id` / `score` / `text` / `book_name` / `author` / `publisher` / `edition` / `price` / `has_notes`。

> `text` 是**真正被向量化的那段文本**（`compose_text` 的产物），不是卖家原文。
> 留它是为了出问题时能一眼看出「到底拿什么去检索了」。
> 卖家原文走 `GET /api/posts/{post_id}`。

#### 决策点

| # | 决策 | 推荐值 | 说明 |
|---|---|---|---|
| 1 | 相似度阈值 `min_score` | ⬜ **待你拍板** | **不设阈值会出现「乱召回」**——问「量子力学」也返回高数 |
| 2 | 相似度算法 | ✅ 余弦相似度 | Chroma 用 `metadata={"hnsw:space":"cosine"}` 显式指定 |
| 3 | 要不要加结构化过滤 | ✅ 先不加 | 如「50 元以下」→ 用 SQL 过滤，不是向量检索的活 |

**决策 1 的起步数据**（用上面那个参考拼法，在 220 条真实帖子上实测）：

| 组 | query | 最高分 |
|---|---|---|
| 正例 | 同济版高数 | **0.6258** |
| 反例 | 量子力学 | **0.4819** |

→ 中间有一条缝，阈值取 **0.55** 左右能分开。跑 `scripts/try_search.py` 会打印完整分布。

> ⚠️ 两个坑：
> 1. **绝对值会随语料规模漂移**。40 条语料时同一条 query 能到 1.0000，220 条只有 0.6258。
>    所以阈值必须用**全量语料**标定，不能照抄网上的 0.7 / 0.8。
> 2. 我给你的调参脚本里**故意绕过了阈值直接查向量库** —— 过滤之后就看不见
>    「反例最高多少分」了，就没法定阈值。

> **决策 3 是个重要的认知**：语义检索擅长「模糊匹配」，**不擅长精确过滤**。
> 「50元以下」「只看有笔记的」这类应该走数据库 `WHERE`，不是向量库。
> 到 M3 设计工具时会用到这个区分。

#### 验收标准

- [x] 输入「同济高数」→ 排第一的是《高等数学》（实测 top-1 = 0.6187）
- [x] 输入「计算机网络」→ 能召回对应帖子（实测 top-1 = 0.6942）
- [x] **输入「量子力学」→ 返回空列表**（实测 `count=0, hits=[]`）
- [ ] ~~输入「带笔记的便宜线代」→ 能召回线代且 `has_notes=true` 的靠前~~
      **→ 已挪到 M3。** 实测整句丢给向量检索返回空（0.5606 < 阈值 0.58）：
      「带笔记」「便宜」这类条件词会**稀释查询向量**，每个词约 −0.07 且累加。
      根因在查询侧，调阈值治标不治本。正确解法是 agent 拆解 → 见 §6.4。
      详见 [面试素材.md](面试素材.md) 第 13 条。

## 6. M3 — Agent

### 6.1 目标

从「调函数」升级到「Agent 自己决定调哪个函数」。

### 6.2 工具设计（决策点）

#### 【新增工具】至少两个

| 工具名 | 作用 | 数据来源 |
|---|---|---|
| `search_books` | 语义检索找书 | M2 的 `/search`（本地） |
| `get_post_detail` | 查帖子详情 | **回调 Spring Boot** `GET /api/posts/{id}` |

**第二个工具是关键**——它是「双服务架构」在 Agent 上的体现，面试可展开。

#### 可选工具（时间够再加）

| 工具名 | 作用 |
|---|---|
| `filter_by_price` | 按价格筛选（走 SQL，不是向量检索） |

#### 决策点

| # | 决策 | 推荐值 | 说明 |
|---|---|---|---|
| 1 | 工具用 `@tool` 装饰器还是手写 | `@tool` 装饰器 | LangChain 标准做法 |
| 2 | Agent 用框架还是手写循环 | **先手写一遍，再换框架** | 手写一次才真懂 tool calling |
| 3 | 要不要多轮记忆 | 要，用 `session_id` | 面试常问 |
| 4 | 最大工具调用轮数 | 5 | 防止死循环 |
| 5 | **会话历史存哪** | ⬜ **待拍板** | 牵涉两条铁律，见下 |

#### ⚠️ 待决策：会话历史存哪

`session_id` 只能**区分**会话，**存在哪**还没定。这个决策牵涉两条铁律：

| 方案 | 结论 |
|---|---|
| Python 进程内存（LangChain `InMemoryChatMessageHistory`） | ❌ 违反铁律二（Python 无状态），且 uvicorn 一重启历史全丢 |
| Python 侧 SQLite / Redis（`SQLiteChatMessageHistory` / `RedisChatMessageHistory`） | ❌ 同上——Python 不该有自己的持久化 |
| **MySQL，由 Spring Boot 拥有，Python 通过 REST API 读写** | ✅ 符合两条铁律 |

**LangChain 自带的几个 history 实现，全部违反铁律。** 这本身就是个可讲的点：
框架给你的默认方案，不一定符合你的架构约束。

选第三种的话，Spring Boot 侧要加：一张 `chat_message` 表 + 读写接口。

### 6.3 接口契约

#### 【新增】`POST /chat` — Python 侧

| 入参 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message` | string | 是 | 用户消息 |
| `session_id` | string | 否 | 会话 ID，不传则新建 |

出参：`session_id` / `reply`（给用户看的回答）／ `tool_calls`（调了哪些工具）。
`tool_calls` 每项含 `name` / `arguments` / `result_count`。

**设计要点：`tool_calls` 必须暴露出来。** 演示时能展示「Agent 自己决定调了什么工具」——
只有 `reply` 的话，看不出它是真 Agent 还是硬编码。这是整个项目最直观的加分项。

错误码：400（message 为空）、504（工具调用超时，如回调 Spring Boot 卡住）

### 6.4 验收标准

- [ ] 问「有高数吗」→ Agent 自主调用 `search_books`，然后组织回答
- [ ] 问「你好」→ **不调工具**，直接回答（验证它真的在做决策，不是无脑调）
- [ ] 问「第一条多少钱」→ 能结合上下文（验证记忆）
- [ ] 问「50 元以下的高数」→ 正确选择用价格过滤而不是硬问向量库
- [ ] 问「带笔记的便宜线代」→ 拆成 `search_books("线代")` + `has_notes=true` / 价格过滤，
      **而不是**把整句丢给向量检索（后者实测返回空 → 见 §5.2 挪过来的那条）
- [ ] 打印完整对话轨迹，能看到工具调用的输入输出

## 附录 B：命名与格式约定

1. **Python 侧字段用 snake_case，Java 侧用 camelCase**，靠 `@JsonProperty` 映射
2. **时间**：Java 端 `LocalDateTime`，JSON 里用 ISO 格式 `2026-10-01T12:00:00`
3. **价格**：Java 端 `BigDecimal`，Python 端 `float`，JSON 里是数字不是字符串
4. ⚠️ **Java 服务配了 `jackson.default-property-inclusion: non_null`**——
   为 `null` 的字段**不会出现在 JSON 里**，前端拿到的对象可能缺字段。
   写前端时要按「字段可能不存在」处理，不要假设一定有。
5. **错误响应格式**：Java 侧统一 `{"error": "...", "detail": "..."}`；
   Python 侧用 FastAPI 默认的 `{"detail": "..."}`
