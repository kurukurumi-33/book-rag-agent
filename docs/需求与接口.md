## 2. 两条铁律

开发和面试都会围绕这两条，任何时候都不许违反：

### 铁律一：AI 服务不直连业务数据库

```
允许：ai-service/app/ 通过 HTTP 调 Spring Boot 的 /api/xxx 拿数据
禁止：ai-service/app/ 里出现 pymysql / SQLAlchemy 连 book_agent 库
例外：ai-service/scripts/ 下的开发脚本可以直连（它们是工具，不是服务）
```

为什么：业务逻辑（校验、事务、权限）集中在主服务。如果 AI 服务也直连 DB，以后加权限校验要改两个地方。

### 铁律二：业务数据的主人是 Spring Boot

Python 负责「理解」（抽取、向量化、检索、对话），
Java 负责「业务」（增删改查、状态流转、事务）。

Python 的服务是**无状态**的：文本进，结果出，不存业务数据。

## 4. M1 — 抽取落库

### 4.1 这一版要解决什么

把已经能跑的抽取能力（`app/services/extract.py`），变成数据库里真实存在的结构化数据。

做完后：`SELECT COUNT(*) FROM book_post WHERE extract_status='DONE'` 应该等于总条数。

### 4.2 数据流

```
Spring Boot                          Python AI 服务
POST /api/posts/extract-pending
   │
   ├─ 查 extract_status='PENDING' 的帖子
   │
   ├─ HTTP POST /extract/batch ─────►  批量抽取（内部并发）
   │◄────── 返回 results 列表 ─────────┤
   │
   ├─ 逐条写回结构化字段
   ├─ 成功的置 extract_status='DONE'
   ├─ 失败的置 extract_status='FAILED'
   └─ 返回统计 {total, done, failed}
```

### 4.3 接口契约

> 字段细节实现后以 **Swagger 为准**（http://localhost:8000/docs）。
> 这里只记 Swagger 表达不了的**设计要点**。

#### 【新增】`POST /extract/batch` — Python 侧

| 入参 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `texts` | string[] | 是 | 帖子原文列表，最多 200 条 |
| `max_concurrency` | int | 否 | 最大并发数，默认 8 |

出参是 `results` 数组，**顺序与请求严格一致**，每项三个字段：
`raw_text`（原样回显）／ `book_info`（失败时 null）／ `error`（成功时 null）。

设计要点：单条失败不中断整批。批量抽取必然有个别失败，
整批抛错等于前面成功的全白跑。调用方靠 `raw_text` 或下标对齐。

错误码：400（空 / 超 200 条 / 并发数 < 1）、500（整批性异常，如 key 失效）

#### 【新增】`POST /api/posts/extract-pending` — Java 侧

编排端点。主服务主动驱动，AI 服务只被动响应。

入参 `limit`（默认 50，上限 200）；出参 `{total, done, failed, failedIds}`。

错误码：400（limit 超 200）、**503（Python 服务连不上——必须捕获，不能让它 500 崩掉）**

#### 【已有】`POST /extract` — Python 侧

单条抽取，已实现。留着调试用，字段见 Swagger。

### 4.4 需要你拍板的地方

| # | 决策 | 推荐值 | 影响 |
|---|---|---|---|
| 1 | 一次批量处理多少条 | `limit=50` | 太大容易超时，太小要调很多次 |
| 2 | Python 侧并发度 | 8 | 太大打 429 限流 |
| 3 | 单条失败怎么处理 | 置 `FAILED`，**不重试** | 重试逻辑留到以后再补 |
| 4 | 失败的帖子怎么再处理 | 下次用 `?status=FAILED` 重跑 | 需要的话再加，现在是 PENDING |

**决策记录**（已定，两个数都配在 `application.yml` 里，不写死在代码里）：

```
1. 一批 = 50 条（ai-service.batch-size）
   理由：单条抽取实测约 1 秒，50 条 ÷ 并发 8 ≈ 7 秒。一批的耗时远低于 HTTP 超时线，
        再往上加批量收益递减 —— 反正调用方要反复调，一批小一点失败重跑的代价也更小。

2. 并发度 = 8（ai-service.max-concurrency）
   理由：DeepSeek 单账号并发上限保守估计 10~20，取 8 留一倍余量防 429 限流。
        实测 50 条只用 7.2 秒，说明 8 已经吃满了这一批的并行度，继续加收益递减。

3. 单条失败：置 FAILED，**不自动重试**
   理由：失败原因没解决时自动重试 = 反复烧 token。留个 FAILED 标记可见可查，重试由人决定。

4. 重试方式：手动把那行的 extract_status 改回 PENDING
   （`?status=FAILED` 参数暂不做，1 万条实测零失败，没有实际需要）
```

**实测数据**：**1 万条分 200 轮跑完（50 × 200），零失败，单轮约 1 秒，全程 3.3 分钟。**
（220 条时代是 5 轮、不到 40 秒 —— 扩容后重新完整跑过一遍，成功率结论不变。）

> 这里有个容易被误读的点：**1 万条 3.3 分钟不是「线性变快了」**，
> 而是官方脚本 `scripts/backfill_extract.py` 内部一直循环到 `picked=0` 为止，
> 单轮 50 条并发 8 真的只要 1 秒左右。把轮数摊开看，耗时仍然是「条数 ÷ 并发」的量级。

## 5. M2 — 语义检索

这是 RAG 的 **R**。分三步走。

### 5.1 M2-1 建索引

#### 目标

把抽取好的结构化字段拼成一段「检索文本」，做 embedding，存进向量库。

#### 为什么不能直接拿 `raw_text` 做 embedding

`raw_text` 里混着「40」「包邮」「可小刀」这些噪音，会稀释掉「高等数学」这个核心语义。
**先抽出干净字段，检索质量才有保证**，这也是 M1 存在的意义。

#### 决策点

| # | 决策 | 结论 | 说明 |
|---|---|---|---|
| 1 | **embedding 模型** | 本地 BGE `bge-small-zh-v1.5` | DeepSeek 没有 embedding API，必须另选。见下方备选对比 |
| 2 | **检索文本怎么拼** | `compose_text` = 书名 + 版次 + 作者 + 出版社 | 这是最关键的设计决策，实测对比见下 |
| 3 | 抽取不全的帖子进不进库 | 只跳过抽不出**书名**的 | 只有成色+价格、没有书名的记录跟「这是哪本书」完全无关，进库就是纯噪音（1 万条里跳过 3 条） |
| 4 | 向量库选型 | Chroma（嵌入式，零配置） | 也可用 FAISS。Chroma 是进程内库，不用起 Docker |

**决策 1 的备选方案**：

| 方案 | 成本 | 说明 |
|---|---|---|
| **本地 BGE**（已选） | 免费 | `sentence-transformers`，首次下载约 100MB（走 `hf-mirror.com`），之后离线。**面试现场断网也能演示** |
| 通义 / 智谱 embedding API | 有免费额度 | 要再注册一个 key，且演示依赖网络 |

**决策 2 的最终拼法（实测过，不是拍脑袋）**：

```
高等数学 第七版 同济大学出版社
```

即 `book_name + edition + author + publisher`，**只有四个字段**。三条被实测否掉的路线：

| 否掉的拼法 | 实测后果 |
|---|---|
| 拼 `condition_desc`（有笔记/九成新） | 「有笔记」这种词对**所有**带笔记的书都成立，等于给查询向量掺通用词，不增加区分度 |
| 拼 `price` | 价格是**过滤条件**不是语义特征。「40」「包邮」这类数字会稀释核心语义 |
| 拼 `raw_text` | 噪音最重的一条。这正是 M1 存在的意义 —— 先抽干净字段再检索 |
| 书名在文本里**重复出现** | 反而拉低分数（0.6258 → 0.6054 → 0.5953），不是因为「越像越好」 |
| 用「未知」占位填 `None` | 毒化检索，**全体掉 0.03~0.11**。空字段就该留空 |

> 对比脚本：`scripts/try_compose.py`（内存里算，只看拼法长相，不当评测用）。

#### 接口契约

#### 【新增】`POST /index/build` — Python 侧

| 入参 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `limit` | int | 20000 | 最多拉多少条。客户端按 500 一页翻，总数由这里定 |
| `rebuild` | bool | false | true = 先清空向量库再建。**只有换模型或改拼法时才需要** |

出参：`{fetched, indexed, skipped, collection_count, dim, elapsed_ms, note}`

**设计要点**：

1. 按铁律一，帖子数据**调 Spring Boot 的 `GET /api/posts?extractStatus=DONE`** 取，不直连数据库。
2. 写入用 `upsert` 且 **id = 帖子数据库主键**，所以**重复调用是幂等的**，不需要先清库。
3. `metadatas` 里只存「列表页直接能显示」的字段（`book_name` / `publisher` / `price` / `has_notes`…）。
   帖子详情仍然回主服务 `GET /api/posts/{id}` 取。**向量库是索引，不是业务数据的副本**，
   这样就绕开了「同一份数据存两处、要保证一致」的麻烦。

#### 验收标准

- [x] 能一次把所有 DONE 的帖子灌进向量库（实测 **10000 拉取 / 9997 入库 / 3 跳过，23 秒**，**不花 LLM token**）
      跳过的那 3 条是抽不出书名的，`compose_text` 拼出来是纯噪音
- [x] 重复调用不会产生重复向量（第二次跑完仍是 9997，不是翻倍 —— `upsert` + id 就是主键）
- [x] 向量库记录里能对回主服务（`post_id` → `GET /api/posts/{id}` 通）

> ⚠️ **两个 1 万条才暴露的坑**（详见 `docs/private/环境与依赖操作记录.md` §3.5）：
> 1. **Chroma 单批上限 5461 条** —— 一次写 9997 条直接 `InternalError` 500，
>    必须在 `vector_store.upsert()` 内部切块（本项目切成 2000）
> 2. **主服务单次只给 500 条，且静默** —— 没有 `offset` 参数时第 501 条以后根本取不到，
>    而接口**返回 200、`indexed=500`**，看着完全正常。所以 `limit` 的语义必须写清是
>    「总数」而不是「一次拉多少」，客户端要负责翻页

### 5.2 M2-2 检索实现

#### 接口契约

#### 【新增】`POST /search` — Python 侧

| 入参 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 自然语言查询，**不需要跟帖子用词一致** |
| `top_k` | int | 否 | 返回条数，默认 10，上限 50 |
| `min_score` | float | 否 | 相似度阈值，低于此值不返回。不传则用服务端默认阈值 |

出参 `{query, min_score, count, hits[]}`，`hits` 每项：
`post_id` / `score` / `text` / `book_name` / `author` / `publisher` / `edition` / `price` / `has_notes`。

> `text` 是**真正被向量化的那段文本**（`compose_text` 的产物），不是卖家原文。
> 留它是为了出问题时能一眼看出「到底拿什么去检索了」。
> 卖家原文走 `GET /api/posts/{post_id}`。

#### 决策点

| # | 决策 | 推荐值 | 说明 |
|---|---|---|---|
| 1 | 相似度阈值 `min_score` | **0.61**（已标定，见下） | **不设阈值会出现「乱召回」**，问「考古」也返回高数 |
| 2 | 相似度算法 | 余弦相似度 | Chroma 用 `metadata={"hnsw:space":"cosine"}` 显式指定 |
| 3 | 要不要加结构化过滤 | 先不加 | 如「50 元以下」→ 用 SQL 过滤，不是向量检索的活 |

**决策 1 已经定了：0.61。但重点不是这个数，是「它到顶了」。**

标定过程（1 万条语料，逐档扫）：

| 阈值 | 正例命中 | 反例为空 | 越界查询被拦 |
|---|---|---|---|
| 0.58 | 16/16 | 4/5 | 0/8 |
| 0.60 | 16/16 | **5/5** | 0/8 |
| **0.61** | **16/16** | **5/5** | **1/8** |
| 0.62 | 15/16 | 5/5 | 1/8 |
| 0.65 | 12/16 | 5/5 | 2/8 |

0.61 是唯一的拐点：再上抬就掉正例，再下调就漏反例。缝只有 **0.0153** ——
最低的正例「同济版高数」0.6187，能拦住的最高越界查询「核工程」0.6034。

**为什么不能再往下调了（这是本文档最重要的一段）：**

语料涨到 1 万条之后，**正负样本的分数分布已经重叠**，穷举 6 种候选统计量
（top1 / top1−top2 / top1−均值 / top1÷均值 / 标准差 / 均值）去切一刀，**每一种都重叠**。
最扎眼的一条证据：

> 正例「同济版高数」的 `top1−均值` = **0.0018**，
> 越界查询「教育学」= **0.0070** —— **越界的看起来比正例还自信。**

根因不在阈值，在**双塔（bi-encoder）本身**：query 和文档各自压成一个向量再比夹角，
夹角只反映「整体语义方向」，分不出「这个词是不是真的指同一件事」。
在一个分不开的空间里找分割面，调参必然失败。

复现这张表：`scripts/analyze_threshold.py`（它显式传 `min_score=0.0` 拿未过滤的原始分布，
避免用「已经被这次要评估的规则切过一刀的分布」做循环论证）。

### 5.4 调优结论：阈值到顶了，换打分器（rerank，已做）

本节是 1 万条语料上的最终实测，两段：
**上半段**证明余弦阈值已经到顶（这是 rerank 的立项依据），
**下半段**是 rerank 上线后的实测答复（结论和直觉相反，重点看那里）。

#### 测试集（21 条）

| 类别 | 条数 | 说明 |
|---|---|---|
| 正例 | 16 | 精确书名 / 口语简称 / 作者名，每条都写清期望命中的那本书 |
| 负例 | 5 | 考古 / 葡萄酒 / 区块链 / 钢琴 / 土木工程 —— **逐条查过库，确实是 0 行** |
| 越界查询 | 8 | 库里没有这个学科，但**分数高到阈值拦不住**，单独追踪不计入通过率 |

#### 结果

**21 条用例全过（16 正 / 5 反），阈值 0.61。**
但真正有价值的不是这个通过率，是下面这张「阈值拦不住的越界查询」表：

| 查询 | 撞上的书 | 分数 |
|---|---|---|
| 纺织 | 这个词是怎么来的 | 0.6959 |
| 农业经济学 | 经济地理学 | 0.7301 |
| 法学概论 | 法学方法论 | 0.7004 |
| 建筑学 | 建筑物理 | 0.6707 |
| 国际关系 | 深度关系 | 0.6233 |
| 环境工程 | Linux 环境编程 | 0.6199 |
| 教育学 | 数学 | 0.6158 |
| 核工程 | Java 核心技术 | 0.6034 |

这 8 条**故意留在测试集里当警报**：`eval_search.py::report_known_leaks()` 每次都重新实测一遍，
**如果哪天某条被拦住了，脚本会打印「←rerank 或阈值生效了，可以把这条搬回 CASES」** ——
也就是把「修好了没有」变成一个脚本能回答的问题，而不是靠感觉。

#### 混合检索（BM25）的净增益：清尾部，不是提命中

`scripts/compare_bm25.py` 逐条对比「仅向量」和「向量 + BM25 + RRF」：

- **top-3 只变了 1/16**（计算机操作系统从第 3 升到第 1，算改进）
- **top-10 变了 5/16**，其中最有价值的是「计算机网络」推掉了 6 条重复的《大学计算机基础》

**诚实结论：BM25 的收益在清尾巴，不在提升命中率。**
纯向量做不到这件事 —— 重复帖子（同一本书的不同卖家）的 embedding 几乎重合，
向量检索天然会把它们一起召回；BM25 靠字面词的区分度能把重复的挤下去。
这个结论比「混合检索比纯向量强 X%」更经得起追问。

#### 下一步：rerank（cross-encoder）—— **已实现，M2.5**

阈值这条路的尽头已经用数据证明了（§5.2）。换打分器：

| | bi-encoder（粗排） | cross-encoder（精排） |
|---|---|---|
| 怎么算 | query、文档各自编码成向量，比夹角 | query + 文档**拼在一起**送进模型，逐对判分 |
| 能不能离线索引 | 能（文档向量预算好） | 不能（每次查询都要重算） |
| 能不能看出「这个词指不指同一件事」 | **不能** | 能 |
| 定位 | 粗排（快，从上万条里捞 20 条） | 精排（准，给这 20 条重新排） |

实现：`app/services/rerank.py`，模型 `BAAI/bge-reranker-base`（与 `bge-small-zh-v1.5`
同家族）。链路变成 `混合召回 20 条 → cross-encoder 精排 → 取 top_k`。

**实测结果（和直觉相反，务必记住）：**

| | 无 rerank | 开 rerank |
|---|---|---|
| 正例 top-3 | 16/16 | 16/16 ← 饱和了，没分辨力 |
| **正例 top-1** | **15/16** | **16/16** |
| 反例 | 5/5 | 5/5 |
| 越界查询拦下 | 1/8 | **1/8** |

> **rerank 改善的是排序，不是过滤。** 它没有「修好」上面那张越界表 ——
> 越界那 8 条仍然只拦下 1 条。被它收服的是「本来答对、却排在第 2」的那批。
> 复现：`eval_search.py --no-rerank --save X`，再 `eval_search.py --save Y --diff X`。

**为什么不再加一道「精排分过滤」**（`rerank_min_score` 默认 None）：
精排分区间是**正例 [0.6987, 0.7311] / 越界 [0.5324, 0.7151]** —— 仍重叠，只是窄了很多。
扫描表里 0.70 看着很香（拦 6/8、正例零误杀），但离正例下界只有 **0.0013**：
用 16 条样本在 0.03 宽的空隙里切一刀是过拟合，不是标定。而且**代价不对称** ——
漏一条越界用户看到一本沾边的书，误杀一条正例用户**搜不到本来有的书**。
真要开这个旋钮，先用 `scripts/tune_rerank.py` 在更多正例上重扫。

> ⚠️ 环境上的坑：**rerank 模型不能走 `snapshot_download`**。hf-mirror.com 不支持
> HuggingFace 新的 Xet 协议，会被 302 到 `cas-bridge.xethub.hf.co` 然后 401 / 超时，
> 连 `HF_HUB_DISABLE_XET=1` 都拦不住（两次实测）。改用
> `scripts/download_reranker.py`（`/api/models` 列文件 + `/resolve/main/` 逐个下，
> 绕开 Xet）。细节见 `docs/private/环境与依赖操作记录.md`。

#### 决策点

| # | 决策 | 推荐值 | 说明 |
|---|---|---|---|
| 1 | 工具用 `@tool` 装饰器还是手写 | `@tool` 装饰器 | LangChain 标准做法 |
| 2 | Agent 用框架还是手写循环 | **先手写一遍，再换框架** | 手写一次才真懂 tool calling |
| 3 | 要不要多轮记忆 | 要，用 `session_id` | 面试常问 |

| 5 | **会话历史存哪** | MySQL，Spring Boot 拥有 | 牵涉两条铁律，见下 |

#### 决策 2 结论：两版都写完了，都跑通（2026-10-05）

`chat_once`（手写）和 `chat_once_framework`（`langchain.agents.create_agent`）**并存**，
不是一个替换另一个。对照脚本：`ai-service/scripts/compare_agent.py`。

拿一个**必然要两轮工具调用**的问题各跑一遍（`帮我找带笔记的线性代数，顺便查一下 139 那本的成色`）：

| 比对项 | 手写版 | 框架版 |
|---|---|---|
| trace 条数 | 2 | 2 |
| 工具序列 | `search_books → get_post_detail` | 同 |
| `result_count` | `[5, 1]` | 同 |
| 存下来的历史形状 | `Human → AI(回答)` | 同 |

**核心风险点过了**：手写版是**边跑边记** trace，框架版是**事后从消息列表里扫回来**
（它不给 trace），两条完全不同的路径，产出一致。

**结论一：框架没有让代码变短。** 实测 **手写 38 行 vs 框架 43 行**（不含 docstring）。
框架版**反而多 5 行**，因为那 20 行扫 trace 的代码要自己写。手写版反倒是
"免费"的：`trace.append` 就塞在已有的工具循环里。

> 数行数必须用 AST 把 docstring 挖掉（脚本里已这么做）。按"非空非注释"数会
> 把 `chat_once` 的 48 行 docstring 算成代码，得出"框架省了 40 行"的假结论。

**结论二：框架真正替我们处理的是协议细节。** 它替掉的是 `bind_tools`、
工具派发、工单↔回执的配对（§17 那个 400）、轮数控制。省的是"必须懂协议"这件事。

**已知的对等性缺口（不修，写进面试素材）：** 跑满轮数上限时，手写版 `trace`
里有 5 条记录（边跑边记），框架版 `trace` 是**空的**——它在 `invoke` 抛
`GraphRecursionError` 时就返回了，扫描还没开始。**同样跑满，手写版能告诉你
它试过哪 5 次，框架版什么都不告诉你。**

#### 待决策：会话历史存哪

`session_id` 只能**区分**会话，**存在哪**还没定。这个决策牵涉两条铁律：

| 方案 | 结论 |
|---|---|
| Python 进程内存（LangChain `InMemoryChatMessageHistory`） | 违反铁律二（Python 无状态），且 uvicorn 一重启历史全丢 |
| Python 侧 SQLite / Redis（`SQLiteChatMessageHistory` / `RedisChatMessageHistory`） | 同样违反，Python 不该有自己的持久化 |
| **MySQL，由 Spring Boot 拥有，Python 通过 REST API 读写** | 符合两条铁律 |

**LangChain 自带的几个 history 实现，全部违反铁律。** 这本身就是个可讲的点：
框架给你的默认方案，不一定符合你的架构约束。

选第三种的话，Spring Boot 侧要加：一张 `chat_message` 表 + 读写接口。

**已实现**：`chat_message` 表 + `ChatMessageController` / `ChatMessageServiceImpl`。
Python 侧只通过 `app/services/book_service.py` 走 REST 读写，自己没有持久化。
（顺带印证了上面那句：LangChain 的 `InMemoryChatMessageHistory` /
`SQLiteChatMessageHistory` 一个都没用上，**框架给的默认方案不符合我的架构约束**。）

### 6.3 接口契约

#### 【新增】`POST /chat` — Python 侧

| 入参 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message` | string | 是 | 用户消息 |
| `session_id` | string | 否 | 会话 ID，不传则新建 |

出参：`session_id` / `reply`（给用户看的回答）／ `tool_calls`（调了哪些工具）／
`books`（这一轮涉及的书，给前端渲染卡片）。

`tool_calls` 每项含 `name` / `arguments` / `result_count` / `post_ids`。

**`post_ids` 与 `books` 是 2026-10-05 为 M4 加的**（原契约只有前三个字段）。
原因：M4 验收要求「结果以卡片形式展示（书名 / 版次 / 价格 / 成色 / 原帖）」，
但这些字段**谁都没有**：

- `reply` 是模型写的文字，字段不全、格式不保证
- `tool_calls` 原来只有 `result_count`（几条），没有书
- 让前端自己补也不行：模型只调 `search_books` 时 `arguments` 里只有 `query`，
  **没有 `post_id`**

所以让 trace 带上 `post_ids`，由 `chat()` 去重后回主服务补全成 `books`。
数据流是：

```
工具返回 list[dict]（含 post_id）
  → trace[].post_ids                    ← loop.py 收集
  → _collect_books() 去重 + 按 id 补全   ← main.py 编排
  → books: [{post_id, book_name, edition, price, condition_desc, raw_text, status}]
```

**两个口径不能忘**：`price` 为 null → `"未标价"`（不是 `"面议"`），
`has_notes` 为 null → `"未提及"`（不是 `False`）。补全**复用 `get_post_detail`**
而不是自己再翻译一遍，否则这套口径会有两份、改一处漏一处。

**设计要点：`tool_calls` 必须暴露出来。** 演示时能展示「Agent 自己决定调了什么工具」，
只有 `reply` 的话，看不出它是真 Agent 还是硬编码。这是整个项目最直观的加分项。

错误码：400（message 为空，或 `session_id` 形状不合法）、503（主服务不可用 —— 读写会话历史失败）

> **503 而不是 504**（2026-10-05 改，原写的是 504）：504 的语义是「网关等上游超时」，
> 而当前 `BookServiceError` 覆盖的是「连不上」和「历史读写失败」，都属于 503 的
> 「对方不在」。**没有设置任何超时**，也就没有 504 的场景，不假装处理了没做的事。
> 等真加了超时（比如 `get_post_detail` 回调卡住），再把那种情况单独分出来给 504。

#### 决策 1 补充：响应为什么用 `JsonNode` 透传，不建一套 Java DTO

Python 的响应里有三处**用 Java 类型表达不了**：

```
tool_calls[].arguments   free-form dict —— 参数名由模型和各工具的 schema 决定
books[].price            float | "未标价" —— 联合类型（见 schemas.py 的 BookCard）
books[].edition          可能是 null
```

硬要映射就只能全写 `Object`，等于没类型；写一套完整 DTO 则意味着同一个 schema
在 Python 和 Java 各维护一份；**AI 服务加个字段，Java 这边不报错、只是静默丢掉**，
这正是最难查的一类 bug。

主服务在这条链路上的角色是**转发**不是**理解**，它没有理由认识 `books` 里有哪些字段。
所以原样透传，接口文档的唯一出处是 Python 的 Swagger（`localhost:8000/docs`）。

#### 踩到的坑：Jackson 2 / Jackson 3 同 classpath

Spring Boot 4 / Spring Framework 7 换成了 **Jackson 3**，databind 的包名从
`com.fasterxml.jackson.databind` 搬到了 `tools.jackson.databind`（annotations 包名没动）。

而 classpath 上**同时存在 Jackson 2**（springdoc 带进来的），所以：

```java
import com.fasterxml.jackson.databind.JsonNode;   // ✗ 编译通过，运行期炸
import tools.jackson.databind.JsonNode;            // ✓
```

编译能过、IDEA 补全两个都给，只有真正反序列化时才报：

```
InvalidDefinitionException: Cannot construct instance of
`com.fasterxml.jackson.databind.JsonNode` (no Creators ...)
```

因为 Spring 的 message converter 用的是 Jackson 3 的 ObjectMapper，
它不认识 Jackson 2 的那个 JsonNode 接口。**编译期查不出来，是运行期才炸的。**

#### 顺带确认的一件事：JsonNode 不吃 `non_null`

`application.yml` 里配了 `spring.jackson.default-property-inclusion: non_null`，
所以 `GET /api/posts/{id}` 直接返回实体时，值为 null 的字段会被**整个省掉**
（实测 209 号帖子的响应里干脆没有 `edition` 这个键）。

但这条配置**不作用于 JsonNode**：树上的 NullNode 是节点本身，不是「值为 null 的属性」。
实测 `/chat` 响应里 `"edition":null` 和 `"condition_desc":null` 都原样保留，
跟 Python 那边一致。**前端因此不用为两种风格分别写判断**（判 falsy 即可，不用区分
`null` 和「键不存在」）。

#### 找到并修掉的一个真缺陷：400 说不清哪里错了

`@Valid` 失败时走 Spring 默认错误体：

```
{"timestamp":"...","status":400,"error":"Bad Request","path":"/api/chat"}
```

**没有 message**。调用方（前端 / curl / 别人）只知道「400」，不知道是 `message` 还是
`session_id` 出的问题。前端当时显示的是英文 `Bad Request`。

补了两个 handler（`GlobalExceptionHandler`）：

```
{"message":""}                    → 400 {"error":"请求参数不合法","detail":"message 不能为空"}
{"message":"","session_id":"a/b"} → 400 {"error":"请求参数不合法",
                                        "detail":"message 不能为空；session_id 只能包含字母、数字、下划线、连字符，长度 1~64"}
"{"                               → 400 {"error":"请求体格式错误","detail":"请求体必须是一个 JSON 对象，例如 ..."}
```

**为什么默认体里连 `message` 都没有**（两层原因叠在一起）：

1. `server.error.include-message: always` 只在 BasicErrorController 渲染时生效，
   而这类异常在 `DefaultErrorAttributes` 里给的就是 null
2. 就算给了 null，`spring.jackson.default-property-inclusion: non_null`
   还会把它过滤掉；这条配置对 Map 的 value 也生效，键直接消失

**细节约定**：只取 `getDefaultMessage()`，**不取 `getField()`**，也不拼「字段名：消息」。
因为 `getField()` 给的是 **Java 属性名** `sessionId`，而 JSON 里的键是 `session_id`
（靠 `@JsonProperty` 映射）；拼进去调用方拿着错误信息去查自己发的 JSON，**找不到那个键**。
所以定成：**DTO 上的校验消息自带字段名，且用对外的那套名字**。

#### 一个没修、只记录的行为：`{"message": 123}` 返回 200

Jackson 默认会把标量**强转**成 String，所以数字 `123` 变成字符串 `"123"`，
`@NotBlank` 顺利通过，模型拿到 `"123"` 当成闲聊答了。

要拦住只能全局关掉标量强转（`ALLOW_COERCION_OF_SCALARS`），但那会连带影响
`{"max_concurrency": "8"}` 这类**有用**的宽松解析，是整条 API 的行为变更。
**判断：不值得为一个不痛不痒的输入改全局，记录在案。**

#### 我的一个预测是错的（值得记）

我预判同会话并发会写出 `human, human, ai, ai` 的错乱顺序。**实测没有**，落库仍然是
`human, ai, human, ai`。原因：`ChatMessageService.append` 标了 `@Transactional`，
**一轮的两条消息是一次事务写入的，拆不开**。

残留的问题是**语义的，不是结构的**：

- 两个并发请求**互相看不见对方**（都在对方写库前读的历史）
- 落库顺序 = **谁先跑完谁在前**，不是用户发的顺序

对演示项目无所谓；真做聊天产品的话，前端要按会话串行化请求。

#### 线程安全实测通过

- 5 个不同会话并发打 `/chat`：全 200，2.2s
- **10 / 30 并发打 `/search`：逐字节完全一致**（同一个查询，30 份响应一模一样）
  说明 BGE 单例和 Chroma 客户端在并发下既不崩、也不静默算错

第二条是重点。「没崩」只说明不报错；**「逐字节一致」才说明没算错**。
如果并发下 encode 被别人踩了，分数会漂、排序会变，但服务照样返回 200。

## 8.5 M2.6 — 多模态：以图搜书

**状态：链路已打通（2026-10-09）。合成图验收通过；真实书脊照片已验收一轮，
结果与遗留问题见本节末尾「真图验收」。**

### 目标

学生拍一张书的照片 → 返回图里每本书在库里的帖子。

⚠️ **真实输入不是一张干净的封面照**，是**一排书脊**：二手书群里流传的典型图是
一个书架上十几本书，或者一摞书侧面露出的书脊。这个输入分布直接决定了下面
「抽一批而不是抽一个」的设计 —— 它不是预先想出来的，是被真实图片纠正的。

### 决策：走「图 → 书名 → 复用检索」，**不是**「图 → 向量比相似度」

这是这个功能唯一值得讲的决策。

| | 方案 | 为什么 |
|---|---|---|
| ✅ 采用 | VLM 读图认出一批书名 → 逐本丢进现有 `search()` | ① 语料是**纯文本**的，一条封面图都没有 —— 图像检索要求每本书有封面向量，这份数据里**建不出来**（不是建得慢）② 认出的书名直接进 `search()`，BM25 / RRF / 精排 / 阈值**全部自动生效**，不用为图片另起链路、另标一套阈值 ③ 拍的是书（封面/扉页/书脊），拍图传递的本来就是**文本信息** |
| ❌ 不用 | CLIP 把图编码成向量，和封面向量比 | 要做「找同款封面」、或语料以图片为主（二手服饰/球鞋）时才该用 |

**场景决定架构，不是技术新旧。**

### 决策：抽一批书名，不是一个

一排书脊上有十几本书。只回一个书名等于「随便挑了其中一本」，
而且调用方**看不出另外十几本被丢了** —— 标准的静默降级。

代码里还有一处更隐蔽的：旧版 `_normalize_title` 结尾的 `splitlines()[0]`。
那行是为「模型不听话、回了一整段解释」写的，但在书脊图上，
模型老老实实列了五行，这行代码把第 2~5 行全切掉了 ——
**一个防御性写法变成了主要的功能损失**。

### 两个上限，分开设，差额如实返回

```python
_MAX_BOOKS_PER_IMAGE  = 30   # 识别上限
_MAX_SEARCH_PER_IMAGE = 20   # 检索上限
```

| | 成本 | 上限 |
|---|---|---|
| 识别 | **一次**模型调用。认 1 本和认 30 本一样贵 | 放宽（30），挡的是「模型把整页 OCR 成 200 行」 |
| 检索 | **每本一次**完整链路（BM25 + 向量 + RRF + 精排），全是真算力 | 收紧（20）。实测单次约 280ms，**串行** 20 本 ≈ 5.5 秒 |

⚠️ **两个数字都被真实照片往上顶过一轮**（原来 20/10）：真图里有 17 本，
识别上限 20 截掉 40%、检索上限 10 只搜六成 —— **上限设得比真实输入还紧，
等于把闸门装在了水管中间**。改完 16 本一本没漏，全部搜到。

⚠️ **代价要一起说清楚**：整次 `/search/by-image` 实测 **10~12 秒**
（视觉调用约 6 秒 + 17 本串行检索约 5 秒）。**这很慢。**
不再往下压检索上限，是因为真实输入就是 17 本，压到 10 等于拿「静默丢 7 本」
换「快 2 秒」。真正的解法是让这批检索并发、或改成后台任务轮询 ——
**都没做**（精排是 CPU 密集，线程池能不能真并行我没验证过，
所以不能说「改并发就好了」）。

差额靠两个列表的长度露出来，**这是故意的**：

```
len(results) < len(recognized_books)   →  认出的书超过了检索上限，后面的没搜
```

默默丢掉一半、装作只认出 10 本，比慢一点糟得多。
（回归用例 `test_书上限必须比搜上限宽` 钉住「两个数不能拧成一股」，
`test_认出超过上限时只搜上限本但书名全给` 用**临时改小的上限**验证截断行为 ——
测试不该跟着调优一起改，上一版照着 15/10 写死，上限一调它就红了。）

### 接口

`POST /search/by-image`，请求 `{image, top_k, min_score}`。
限流 **10 次/分钟/IP**（见下）。

`image` 只收两种：base64 data URL、http(s) 直链。
**不收本地文件路径** —— 那等于开了个读任意文件的口子（有专门的用例钉住）。

响应：

```jsonc
{
  "recognized_books": ["高等数学", "线性代数"],   // 模型认出的全部
  "min_score": null,
  "results": [                                    // 真的检索了的，是上面的前缀，同序
    { "book": "高等数学", "query": "高等数学", "count": 2, "hits": [] }
  ]
}
```

`query` 目前恒等于 `book`（识别出的书名直接当查询词）。之所以还单独留一栏：
将来若在检索前做一次改写（比如去掉版次尾巴），那时两者就会分叉，
而「实际拿去搜的是什么」必须是响应里看得见的东西。

排查时看两个地方：

```
recognized_books = []          →  视觉没识别出书（图糊 / 竖排反光 / 没书 / prompt 要调）
某条 count = 0                 →  识别对了，但库里没这本书（检索或语料问题）
```

没有这两栏，两类故障在日志里长得一模一样。

### 书脊是这个功能最难的一档（诚实记录）

书脊上的字小、常竖排、有弧度还反光，被相邻的书挤掉一半也是常事。
GLM-4V-Flash 是免费的小模型，**一定会漏，也一定会认错几本**。两者不对称：

- **漏**（有书没列出来）→ 用户少看几本，但他知道自己拍了几本，能发现。
- **错**（列了一个图里没有的书名）→ 这个名字进检索，库里 2869 个书种，
  它多半能捞回**几条看着挺像的结果**。用户没有任何办法分辨这是真的还是编的。

所以 prompt 里明写「看不清的不要猜」。但那只是降低概率，不是消除 ——
**验收必须拿真图跑，而且要对着原图逐本核有没有编出来的书名**，
只看「有没有命中」是查不出这个失效模式的。

### 真图验收：拿一张真实书架照跑出来的（2026-10-09）

样本：`test-images/wechat-shelf.jpg` —— 微信群二手书帖的原始图，
一个书架 16~17 本书的书脊，字小、竖排、反光、有遮挡，右下角还贴了
「出书 5r 一本」的促销水印。**这是这个功能的真实输入分布，不是构造出来的。**

脚本：`scripts/check_vision.py`（识别结果与命中并排打印，逼你对着原图核）。

**第一轮（改之前）：20 条输出里 6 条根本不是书名。**

```
经济法学》编写组   学生用书   （2021年版）
王振友张丽丽李锋主编   北京大学出版社   吴传生主编
```

当时已有的 `_META_LABEL_RE` **一条都没拦住** —— 它要求行首是「作者：」
「出版社：」这种**带冒号**的标签，而模型实际抄的是书脊上的**裸正文**，
一个冒号都没有。**规则本身没错，错在它假设了输入里有标签。**
（教训：单测 40 条全绿，因为它们测的全是「我想象的输入」。）

危害实测过：`学生用书` 检索出《走遍法国2 学生用书》《新视线俄语1 学生用书》——
**结果页看着完全合理**，用户没有任何线索知道这是在瞎搜。
编一个不存在的书名，用户一眼能看出不对；编一个泛词，看着挺像。

**修的三处：**

1. prompt 里点名列出书脊上那些**不是书名**的东西（署名、出版单位、
   版次、「学生用书」「智慧版」这类标注、以及图上的水印促销文字）。
2. `_normalize_title` 补三条兜底：署名/出版单位后缀、整行只有括号
   （`（2021年版）`）、通用标注停用词。**只收「整行都是」的情况** ——
   `C++ Primer（第5版）` 的括号在中间、`高等教育出版社图书` 不在句尾，都不受影响。
3. 两个上限 20/10 → 30/20，理由是上面那条「上限比真实输入还紧」。

**第二轮（改之后）：16 条，全部是书名，全部搜到，80 条命中。**

漏的变成了「少看几本」（`视听说教程`、被相邻书挤掉一半的那本），
而不是「多出几本查无此书」—— 这正是我们想要的失衡方向。

**仍然存在的问题，如实记着：**

| 现象 | 例子 | 为什么没修 |
|---|---|---|
| 版次被粘进书名 | `经济数学微积分-第4版` | 想剥掉就得先能分清「第4版」是书名的一部分还是书脊上的独立标注。分不清就剥，会把真书名切坏，代价比留个尾巴大 |
| 两本书名被合成一个 | `新时代大学英语`（架上其实是《新未来大学英语》和《新时代大学进阶英语长篇阅读》） | 只能靠人工词表，而词表永远覆盖不到没见过的混淆 |
| 书被挡住就漏 | 最右边那本只露一条边 | 模型看不见就是看不见，这是输入信息的硬上限 |
| **两次跑结果不一样** | 第一轮 20 本、第二轮 16 本 | 温度已经设成 0 了，但视觉模型的前处理仍有随机性。**意味着上面这些数字都是单次观测，不是稳定指标** |

**所以这个功能的上限是「帮你少翻几页」，不是「替你确认书在不在库」。**
要做成可信赖的，得让人工确认那一步留在界面上（图 + 识别出的书名，
用户能勾掉认错的），而不是直接把书名当成事实去检索 —— 这一步**没做**。

### 限流：它按**成本**归类，不按 URL 前缀归类

`/search/by-image` 走的是 `/search` 那条路径、名字也像检索，
很容易被顺手归进「检索不烧 key、不限流」那一类 —— **它就这样漏了整整一个里程碑**。

它必须限流，因为第一步就是一次视觉调用（比文本模型慢一个数量级），
后面还跟着最多 20 次检索。限额 **10 次/分钟，全项目最紧的一档**（比 `/chat` 的 20 还紧）。

（回归用例：`tests/test_routes.py::test_以图搜书没有被漏在限流外面`
+ `tests/test_ratelimit_wiring.py::test_以图搜书也被限流`。）

### 安全边界：视觉输出**只当检索词**，不进任何 prompt

图片是不可信输入 —— 一张图完全可以印着「忽略以上指令」。

本实现里它不可能造成危害，因为识别结果**只有一个出口**：
被当成 query 字符串传给 `search()`。它不进任何 prompt、不进对话历史、不给模型看。
返回一串书名**没有削弱**这条性质：判断标准是「有没有回到 prompt 里」，
不是「返回了几个字符串」。

**「不可信输入终止在检索边界」是设计出来的性质，不是碰巧。**
（回归用例：`tests/test_vision.py::test_识别结果只作为字符串返回不掺进prompt`。）

### 降级

没配 key → `get_vision_llm()` 返回 None → 接口回 **503 + 缺哪个变量**。
别的接口完全不受影响；`/health` 的 `vision.configured` 能一眼看到。

⚠️ **校验顺序**：先查图片参数（400），再查 key（503）。
写反的话，没配 key 时传个非法路径也报 503，让人去查服务端配置、方向完全错。
（第一版就是这么写的，实测抓出来的。）

## 8.6 M4.5 — Redis：限流 + 会话缓存

**状态：已完成。** 单测 14 条 + 真 Redis 集成 14 条，降级路径实测过。

### 为什么 Redis 放在 AI 服务

存的是**运维态**（限流计数、缓存），不是业务数据 —— 所以不违反
「AI 服务不直连业务数据库」那条铁律。限流天然属于「谁提供服务谁负责」，
而 `/chat` `/extract` 是 AI 服务提供的。

### ① 限流：滑动窗口 + Lua

**为什么不用固定窗口**：0:59 打满 → 1:00 计数器归零 → 再打满，
**两秒内实际放行两倍**。滑动窗口（ZSET 存时间戳）任意时刻往前看 60 秒都不超。

**为什么用 Lua**：「清理 → 计数 → 判断 → 写入」四步必须原子。
分开发四条命令，并发下两个请求会同时读到 `count=19` 并同时放行。
**这类 bug 只在并发下出现，本地怎么点都复现不了。**

⚠️ **ZSET 的 member 必须唯一**（用时间戳当 member 的话，同一毫秒的请求会被
当成同一条，高并发下限流悄悄失效）。加随机后缀。

限额：

| 接口 | 限额 | 理由 |
|---|---|---|
| `/chat` | 20 次/分钟/IP | 一次烧一次模型调用 |
| `/extract` `/extract/batch` | 60 次/分钟/IP，**共用一个桶** | 内部调用（建索引连着打几百次），限太紧会限死正常运维。共用桶是因为分开算 = 两倍上限 |
| `/search` `/index/build` | **不限** | 本地 BGE，只烧 CPU。限流限的是成本不是流量 |

**身份取 TCP 对端 IP，故意不看 `X-Forwarded-For`** —— 那个头客户端随便写，
换个值就换一个桶，等于一行命令绕过限流。

### ② 降级：fail-open，但必须吵

Redis 不可用 → 放行 + warning。不是「宁可拒绝服务」——那是计费/风控场景，
Redis 在这里只是可选依赖。

但放行**不等于静默**：启动日志一条 warning + `/health` 的 `redis.connected`。
和 rerank 加载失败、视觉 key 未配置是同一个立场。

⚠️ **连上之后再掉线要重启服务才恢复** —— `get_redis()` 缓存了「连接成功」这个结论。
有意取舍：宁可要「明确的、需要重启的降级」，也不要「每个请求都慢半拍」。

### ③ 会话缓存：cache-aside + **写时失效**（不是写穿）

写穿要求缓存**复刻主服务的截断逻辑**（`limit=20` 时 append 完还得再截），
哪天主服务改了规则，缓存里就留了一份「和接口不一样的真相」——
正是这个项目一直在避免的第二份业务逻辑。

失效则保证：**缓存里要么是主服务真返回过的东西，要么不存在。**
缓存永远不可能比主服务更聪明。

⚠️ 两个容易漏的点，都有回归用例：
1. **key 里必须带 `limit`** —— 否则先读 `limit=2` 再读 `limit=20` 会拿到那份 2 条的缓存，
   表现成「agent 突然失忆」，而且只有改变调用顺序时才复现
2. **`invalidate` 必须删该会话所有 limit 的缓存** —— 只删一个的话，
   写完新消息后 `limit=2` 那份还是上一回合的

### 验证（已做）

- 单测 14 条（假 Redis，测算法与降级分支）
- **真 Redis 集成 14 条**：Lua 真发过去跑（滑动、TTL、拒回最早时间戳）、
  HTTP 层打进去确认**限流真挂在接口上**、缓存命中/失效/不串味
- 实测：往缓存里塞假值 → 再读确实拿到假值（证明读的是缓存）；
  写一轮消息后缓存被删；再读拿到真实数据

### ⚠️ 一个测试方法论的坑

限流的单测用内存假 Redis，**Lua 脚本一行都没被测过** ——
假客户端是用 Python 复刻的滑动窗口语义，Lua 写错了它也看不出来。
**测试和一个错误实现达成了一致。**

所以必须有直连真 Redis 的那一组。这是「测试替身」的边界：
替身能测「调用方怎么用返回值」，测不了「被替身换掉的那段逻辑本身对不对」。

### ② token 成本（M6.2）

`BaseCallbackHandler` 挂在 LLM 客户端上，`on_llm_end` 里从原始 `LLMResult`
掏 `usage_metadata`。

**为什么不在调用处数**：抽取走的是

    llm.with_structured_output(BookInfo, ...).invoke([...])  -> 返回 BookInfo

DeepSeek 的响应本来就带 usage，但 `with_structured_output` 在中间把它解析成了
pydantic 对象 —— **usage 在这一步被丢掉**。要拿到它只有两条路：
自己解析 tool_calls（重写整条链路），或者挂 callback（**一行调用代码都不用改**）。

`GET /usage` 返回累计用量 + 估算成本。实测：

| | 数字 |
|---|---|
| 单条抽取 | 1625 入 + 142 出 ≈ **0.0044 元** |
| 3 条并发批量（`batch_size=1`） | 正确记到 **3 次调用**（并发累加上锁，不丢计数） |
| `calls_without_usage` | 0 —— DeepSeek 这条路能正常拿到 usage |

**专门留了 `calls_without_usage` 一栏**：它 > 0 就说明有调用成功返回但没拿到 usage，
**账目不全**。设它是为了防一件事 ——「统计失效」最容易伪装成「成本为 0 元」：
provider 换个字段名，你会看到一个干净漂亮的 0。

另外补了 `timeout=60` / `max_retries=2`。这是全项目**唯一一个之前没有超时保护的
出网调用**。重试只给 2 次：DeepSeek 的 429 是**账号级**的，重试多了只会把限流打得更死。

## 附录 B：命名与格式约定

1. **Python 侧字段用 snake_case，Java 侧用 camelCase**，靠 `@JsonProperty` 映射
2. **时间**：Java 端 `LocalDateTime`，JSON 里用 ISO 格式 `2026-10-01T12:00:00`
3. **价格**：Java 端 `BigDecimal`，Python 端 `float`，JSON 里是数字不是字符串
4. **Java 服务配了 `jackson.default-property-inclusion: non_null`**：
   为 `null` 的字段**不会出现在 JSON 里**，前端拿到的对象可能缺字段。
   写前端时要按「字段可能不存在」处理，不要假设一定有。
5. **错误响应格式**：Java 侧统一 `{"error": "...", "detail": "..."}`；
   Python 侧用 FastAPI 默认的 `{"detail": "..."}`
