## 演示前 5 分钟：清单

按顺序打勾，漏一步现场就尴尬：

```bash
# ① MySQL 起没起（重启机器后它不会自己起）
net start MySQL80

# ② 两个服务
cd book-service && mvn spring-boot:run
cd ai-service && ./.venv/Scripts/python.exe -m uvicorn app.main:app --port 8000

# ③ 探活
curl http://127.0.0.1:8000/health      # {"status":"ok",...}
curl http://127.0.0.1:8080/api/posts   # 有 JSON 就对了
```

- [ ] **④ 预热**：这条最容易被忽略。
      BGE 模型是第一次检索时才载入内存的。不预热的话，等你当着面试官的面
      发出第一句话，会先卡两三秒（还在加载模型），而这正好是全场最需要流畅的时候。
      预热方法：自己先发一次 `/search`，把权重载进来：
      ```bash
      curl -X POST http://127.0.0.1:8000/search -H "Content-Type: application/json" \
           -d '{"query":"线性代数","top_k":3}'
      ```
- [ ] **⑤ 先自己完整走一遍三幕**。走通了再叫人来看。
- [ ] **⑥ 浏览器开无痕窗口**，只留这一个 tab。无痕 = 没有插件、没有历史记录干扰。
- [ ] **⑦ 三个问题提前打好**放在记事本里，现场复制粘贴。
      （现场打字一打错，模型可能给出完全不同的回答，脚本就对不上了。）
- [ ] ⑧ **截图存本地**。万一没网 / API 挂了，切截图讲，比现场卡住强。
- [ ] ⑨ **要讲第四幕的话，额外做两件事**：确认 `ai-service/.env` 里
      `VISION_API_KEY` 还在（**别把它贴进任何演示用的聊天窗口 / 记事本**）；
      把 `test-images/wechat-shelf.jpg` 提前拖到桌面，现场直接拖进上传框，
      别在现场翻文件夹。
      **预热也要多预热一个**：视觉那次调用本身就是 ~6 秒，第一遍会更慢，
      讲第四幕之前先自己传一次把连接热起来。

## 时间轴

| 时间 | 干什么 | 要让人看到什么 |
|---|---|---|
| 0:00–0:20 | 一句话说清这是什么 | RAG + Agent 导购，跟 CRUD 项目不同 |
| 0:20–1:00 | **第一幕**：条件检索 | 模型自己拆出 `has_notes` / `price_max` |
| 1:00–1:30 | **第二幕**：追问某一本 | 多轮记忆 + 回调主服务取详情 |
| 1:30–1:50 | **第三幕**：问一本没有的书 | 阈值拒识，不返回 top_k 垃圾 |
| 1:50–2:10 | **第四幕**（可选）：以图搜书 | 拍照就能搜，且成本/代价说清 |
| 2:10–2:20 | 收尾 | 一句话点架构 |

第四幕是**可选的兜底**：时间不够就砍它，三幕已经完整。
时间富余、或者面试官对 RAG 无感时，用它翻盘。

## 逐句脚本

### 0:00 开场（20 秒）

> 「智觅 —— 一句话找到你要的二手书。跟普通的 CRUD 不一样的地方是：
> 用户搜书说的是人话，『带笔记的线代，别超过 30 块』，
> 而库里存的是卖家发的原始帖子，完全没结构。
>
> 所以中间有两条链路：**一条 RAG**，把帖子抽成结构化字段、向量化、建索引；
> **一条 Agent**，用户提问之后，模型自己决定调哪个工具、调几次。
> 我演示的是第二条。」

### 0:20 第一幕：条件检索（40 秒）

**输入这句**（复制粘贴）：

```
有笔记的线性代数，30 块以内
```

指着屏幕上那栏「🔧 Agent 的工具调用」说：

> 「这里，模型把它拆成了一个 `search_books` 调用，
> 参数是 `query="线性代数"`、`has_notes=true`、`price_max=30`。
> **这三个参数没有任何一行代码写死**，是模型从这句话里自己提的。
>
> 注意分工：『是哪本书』走向量检索，『什么条件』走结构化过滤，
> 因为『有没有笔记』『多少钱』这种条件，向量是搜不准的，必须精确匹配。」

**实测输出**（5 张卡）：

| 编号 | 书名 | 价格 |
|---|---|---|
| 139 | 线性代数（第六版） | ¥8 |
| 133 | 线性代数（第六版） | ¥12 |
| 124 | 线性代数（第六版） | ¥15 |
| 98 | 线性代数（第六版） | ¥12 |
| 85 | 线性代数（第六版） | ¥8 |

### 1:00 第二幕：追问（30 秒）

注意：**必须用下面这句原话。** 别说「139 那本」，见文末「已知的坑」。

**输入**：

```
那 8 块那本呢，成色和还在不在售？
```

> 「注意这里的两个动作：模型先**又搜了一次**确认候选，
> 然后拿它自己选中的 `post_id=139`，**回调 Spring Boot 的
> `/api/posts/139`** 去取完整信息 —— 成色、卖家原话、还在不在售。
>
> **这一步是重点**：AI 服务不连数据库。它要帖子数据，得走主服务的 REST 接口。
> 所以你会看到 `get_post_detail` 这个『本地工具』，实际上是一次跨进程 HTTP 调用。」

**实测输出**：

> 139 号这本（¥8）的情况：
> - **成色/笔记**：有笔记，划过重点
> - **版本**：同济第六版
> - **状态**：在售
>
> 另外还有一本 ¥8 的是 85 号，需要的话我也可以帮你查。

（最后那句是模型自己注意到 85 也是 8 块，不是我让它说的。）

### 1:30 第三幕：问一本库里没有的书（20 秒）

**输入**：

```
有没有量子力学的书
```

> 「会说没有。**这一条是我特意留的演示点**。
> 向量检索有个特性：**它永远会返回 top_k 条**，哪怕库里压根没这本书。
> 你要是直接把 top 5 丢给模型，它就会一本正经地推荐五本高数。
>
> 所以我加了相似度阈值 0.61。验一下给你看。」

**（可选，如果时间够）开个终端跑这条命令对比**：

```bash
curl -X POST http://127.0.0.1:8000/search -H "Content-Type: application/json" \
     -d '{"query":"量子力学","top_k":5,"min_score":0.0}'
```

**实测输出（关掉阈值后）** —— ⚠️ **下表是 220 条语料时测的，换成 1 万条后必须重测**：

| 分数 | 书名 | 编号 |
|---|---|---|
| 0.4819 | 高等数学 | 209 |
| 0.4819 | 高等数学 | 187 |
| 0.4819 | 高等数学 | 125 |
| 0.4819 | 高等数学 | 104 |
| 0.4819 | 高等数学 | 25 |

> 「搜『量子力学』，返回五本『高等数学』，相似度 0.4819，
> 全是垃圾，但向量库不会告诉你它们是垃圾，它只是忠实地返回最近的五个。
> 所以 0.61 这个阈值应该算正确性的一部分。」

**说这段话的正确姿势**：重点**不是**那个具体的 0.4819，而是
「关掉阈值它一定会返回 top_k 条垃圾」。数字变了没关系，结论不变；
但如果被追问「这个分数现在是多少」，**得当场测得出来**，不能报旧数。

### 1:50 第四幕（**可选**）：以图搜书（20 秒）

**什么时候用这一场**：面试官明显对「Agent / 工具调用」不感兴趣，或者你已经讲完
三幕还有时间。这一场是**视觉冲击最大**的一场 —— 前面全是打字，这一场是拍照。

**怎么演示**：直接拖一张**真实书架照**进前端的上传框（不是封面图，是书脊照 ——
书脊才是难点）。本机 `test-images/` 里有张 `wechat-shelf.jpg`，就是真跑过的那张
（**照片本身不进仓库，仓库里只有 `test-images/README.md`**，里面写明该放哪几张图；
clone 的人自己拍一张放进去即可）。

> 「前面都是打字。但真实场景里很多二手书卖家是**拍一张照**就发过来。
> 所以我也支持以图搜书。
>
> 做法不是给图片建索引 —— 语料是纯文本的，**图像索引根本建不出来**，不是慢。
> 走的是『图 → 视觉模型读出一批书名 → 复用刚才那套文本检索』。
> 换句话说我一个字都没为多模态新增检索代码，只加了一只眼睛。」

**实测（2026-10-09，真实书架照）**：

| | 改 prompt 前 | 改 prompt 后 |
|---|---|---|
| 认出的条目 | 20 条 | 16 条 |
| 其中**根本不是书名**的 | **6 条** | **0 条** |
| 实际发起检索 | 10 本（撞上限） | 16 本 |
| 命中帖子 | 49 | 80 |

**主动交底**（这一段才显出你真跑过）：

> 「改之前它会把书脊上印的『高等教育出版社』『学生用书』当成书名 ——
> 这种**编出来的泛词比编书名更危险**，因为搜『学生用书』还真能搜出东西来，
> 用户看不出错。改完之后 16 条全是书名。
>
> 但有个我自己没解决的问题：**同一个输入跑两遍结果不一样**，16 本 vs 20 本。
> 温度已经是 0 了还是这样，说明视觉模型这一档本身不稳。
> 所以这个功能我定位成『帮你少翻几页』，不是『替你确认书在不在库』。」

**耗时**：整次请求 **10~12 秒**（视觉约 6 秒 + 检索约 5 秒），
要当场说一句「慢在这，真正的解法是把这批检索并发跑或者改后台任务轮询，**我没做**」。
（串行是显然的：单次 `/search` 中位 280ms × 16 本 ≈ 4.5 秒。）

### 2:10 收尾（10 秒）

> 「整个东西是双服务的：Java 管业务和数据，Python 管理解和检索，
> AI 服务不碰数据库。这样做的好处是换模型、换向量库只动一边，
> 而且 AI 服务完全无状态，可以随便重启。」

## 翻车预案

| 出什么事 | 怎么办 |
|---|---|
| **模型 API 挂了 / 超时** | 别慌，切到 `/search` 演示：「检索链路不依赖大模型，我用接口直接演示。」第三幕那条命令就是现成的 |
| **完全没网** | 切本地截图讲。**所以第 ⑧ 条要提前做** |
| **模型抽错参数了** | **别藏。**「这次它把 has_notes 漏了 —— 这是 temperature=0 也会偶发的，工具描述还能再改。」推过责任比假装没看见强 |
| **回答很长 / 跑题了** | 别等它说完，直接说「我打断一下，这个回答本身不是重点」然后接着讲你的 |
| **服务起不来** | `curl /health` 定位是哪个没起。**先查 MySQL80**，它是手动启动的，最容易忘 |
| **以图搜书超时 / 报错** | 十有八九是 `VISION_API_KEY` 没配或视觉模型那边抖。**直接切下一幕**，花 10 秒解释「这一路要调外部视觉模型，现场网络不稳」，比现场 debug 体面。**别为了救它把时间耗光** |
| **以图搜书认出的一堆书里有一本明显不对** | **主动点出来**：「这条它编了 —— 书脊是最难的一档，模型会漏也会编，这也是我把上限设成『帮你少翻几页』的原因。」**自己指出来是加分，被面试官指出来是减分** |

## 已知的坑：别说「139 那本」

实测（2026-10-05）：

| 你说 | 结果 |
|---|---|
| 「那 8 块那本呢，成色和还在不在售？」 | 能：正确触发 `get_post_detail({'post_id': 139})` |
| 「139 那本成色怎么样？」 | 不能：模型把 139 当成价格，回「没有 ¥139 的」 |
| 「139 号帖子那本，成色怎么样？」 | 不能：模型答「search_books 返回的摘要不带帖子编号，我定位不了」 |

**第三行是错的** —— `search_books` 的返回值里**有** `post_id`，
我复现过模型收到的那串文字：

```
[{'post_id': 139, 'book_name': '线性代数', 'price': 8.0}, {'post_id': 133, ...}, ...]
```

`post_id` 就明明白白在里面。**模型是在否认自己收到的输入。**

**为什么「8 块那本」就能成**：模型自己调 `get_post_detail` 拿回来的结果里有 `post_id`，
它拿着这个 id 就会用了；但**用户报给它的 id，它连不回上一轮的搜索结果上**。

**根因（两条，都还没改）**：

1. 工具结果是 `str(list_of_dicts)` —— 一串 Python `repr`，
   单引号、没标签、五个字典挤成一行，`post_id` 混在噪声里不显眼。
   **改成 `json.dumps(..., ensure_ascii=False, indent=2)` 会好很多。**
2. 系统提示里其实写了「先从 search_books 的结果里拿到那本的 post_id」，
   但模型没照做 —— **提示词写了不等于模型会执行**。

**目前不去改**：改了要重跑全部验收。演示绕开这个措辞就行。
（面试时被问到可以主动说 —— 「我知道这儿有个措辞脆弱点，根因是工具结果没格式化」。）

## 演示时最容易被问的三个问题

| 问 | 答 |
|---|---|
| 「这个检索是你自己写的还是调库？」 | 「向量库用 Chroma，**但检索策略是我定的**：相似度阈值 **0.61** 是我用 **21 条用例（16 正 / 5 反）** 逐档扫出来的：能拦住的最高越界查询 **0.6034**、最低正例 **0.6187**，**缝只有 0.0153**」 |
| 「工具调用是模型决定的还是你写死的？」 | 「模型决定的。我控制的是**给了它哪几个工具**和**最多循环几轮**（`recursion_limit=12`），具体调哪个、调几次是它自己选的」 |
| 「AI 服务为什么不直接连数据库？」 | 「那样它会持有状态，就没法随便重启、没法扩多副本。现在它要数据就调主服务的接口，代价是多一跳 HTTP」 |
| 「以图搜书准吗？」（第四幕必被问） | 「**书脊是最难的一档，会漏也会编。** 真图实测：改 prompt 前 20 条输出里 6 条根本不是书名，改后 16 条全是书名。**但同一个输入跑两遍结果不一样**（16 本 vs 20 本），所以它是『帮你少翻几页』，不是『替你确认书在不在库』」 |
| 「为什么不用 CLIP 做图搜图？」 | 「CLIP 要求**每本书都有封面图**才建得出索引 —— 我这份语料是纯文本帖子，**图像索引根本建不出来**，不是慢。所以走『图 → 书名 → 复用文本检索』，一个字的多模态检索代码都没写」 |
